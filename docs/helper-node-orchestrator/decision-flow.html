Orch v2.1.1 Decision Flow

Nothing about your servers is built into the skill. The first time it runs in a project it asks how many helpers, how to reach each one, then production and deploy details, and saves the answers in the project. Every later session checks the saved setup and shows one line, or asks only for what is missing. Heavy work then goes through one orch command to the helper that is allowed, safe right now and has the most room, and every step lands in the project journal. Pick a story to watch it.

    Machines and how one is chosen

    names, addresses and numbers are example answers
    1 · Heavy or light

    Reading, editing, planning, git and the deploy command stay on the master. Builds, installs, tests, lint, suites and image builds go to a helper. Unsure counts as heavy.

    2 · Allowed there

    Reachable, Docker up, not paused, and the job fits the helper's scope: everything / lint + tests (no image builds) / read-only commands / nothing. Only if you give a helper the production role too (not in this example) is it read-only unless you pick lint + tests.

    3 · Safe right now

    Free memory − job ≥ 25% of the helper. PSI avg10 < 10, swap < 50 pages/s, disk ≥ 15% and 20 GB free, inodes ≥ 10%, load1 < 0.85 × CPUs. A missing memory or disk reading rejects.

    4 · Best of the rest

    Score = 0.5 × memory room + 0.3 × idle CPU + 0.2 × affinity. One heavy job per helper; a dedicated helper may run 2 (max_heavy, after your approval); a production server always 1. Nothing free: orch waits up to 10 min, then exit 75.

    What the journal holds

    orch journal show · orch journal stats [--json]
    start / end

    The agent opens every task with summary, request and plan, and closes it with outcome (done, partial, failed, blocked), summary, lessons and what is still open. orch adds the duration.

    decision

    What was decided, why, and the options. The agent records its own; orch records each setup answer you give.

    step

    orch records every command by itself: verb, job, helper, admission, retries, result and seconds. The agent adds the deploy or rollback command it ran.

    difficulty / resolution

    orch records its own failures and marks them resolved when the same command later passes. The agent adds problems orch cannot see, and how each was fixed.

    What keeps helpers and production safe

    Guard hook

    Every tool call on the master is checked first, MCP tools too. Heavy work on the master, or raw docker, ssh-docker or file copies toward a helper, is denied with blocked: <what>; use: <orch cmd>.

    Production read-only

    Read-only commands toward production are allowed, destructive ones denied, anything else asks you. Changes go only through the saved deploy or rollback command.

    Your setup is yours

    The agent cannot write orch's store, trust or guard files, set orch's variables, or approve: approval is your permission prompt. Loosening changes need a new approval.

    Own items only

    orch touches only names that start with agentx- and carry the io.orch.agent label. Anything else on a helper is reported, never removed.

    Secret scan

    Source leaves the master as a git archive (--wt adds uncommitted files), scanned for keys and tokens first. A hit stops the job with exit 2. source_allow can exempt one exact file per entry (a test fixture), matched case-exact; adding one needs your approval. Setup answers holding a secret are refused.

    No network in tests

    Prep gets its own /28 network and a cache volume; the network is cut before tests start. Phase markers count only with the per-job nonce.

    R1 watchdog

    Every 10 s it checks the helper's own apps: container fingerprint, PSI < 25, iowait < 30%, watched URLs < 2× + 0.2 s. Three bad checks kill the job and pause the helper for 30 min.

    Few tokens

    Jobs run in the background, independent ones together. The agent reads only the final JSON line, brief logs on failure, and replies one line per job.

    New in v2.1 and v2.1.1

    every loosening asks for your approval first
    Two heavy jobs

    hosts.<name>.max_heavy 1 or 2 lets a dedicated helper run two heavy jobs at once. A helper that is production here or in another project always runs 1.

    Policy answer

    policy overrides the defaults in orch init --apply. Safety floors hold (reserve ≥ 20%, PSI ≤ 25, max_heavy 1..2); a non-object or NaN value is refused; every change needs approval.

    Health via IP

    A health URL can take "resolve": "<IP>" like curl --resolve: orch connects to that IP, sends the name as SNI and Host, and never goes through a proxy.

    Deploy-only production

    reach: deploy-only marks a production server only the deploy command reaches. orch never probes it; the reachability gate warns instead of failing.

    Exact-file exemptions

    source_allow entries name one file each: ^src/tests/fixtures/fake-key[.]pem$. Wildcards, repeats, groups and alternatives are refused; matching is case-exact to the true end.

    Approval on loosening

    Raising a helper's effective capacity, a new or renamed job with source_allow, deploy-only reach and policy changes all wait for your yes.

    Honest selftest

    A check that cannot run here prints [SKIP] and is not counted as passed, e.g. "Docker down" without a Linux helper.

    Proven

    781 unit tests, 69 guard tests over 882 fixtures, a real local Docker run and a real ssh run on a shared helper, plus two independent reviews.
